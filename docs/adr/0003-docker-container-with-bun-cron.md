# Docker container with Bun.cron() in-process scheduling, not a systemd timer + compiled binary

Ticket 05's initial research recommended a systemd timer triggering a compiled, one-shot `bun build --compile` binary, since that comparison assumed a bare-host deployment with no existing process supervisor. In practice, the Recipient runs every other service on their Oracle server as Docker containers via docker-compose, and wants this project to follow the same operational pattern rather than introducing a one-off bare-host systemd job alongside them. We chose a **long-running Docker container using `Bun.cron()`'s in-process scheduling mode** instead: the container stays up (using docker-compose's own restart policy for resilience) and schedules its own daily/periodic run internally, rather than being invoked externally by the OS. This costs some idle resource usage (the process sits mostly idle ~99% of the day) that a one-shot systemd-triggered process wouldn't incur, which the Recipient has explicitly accepted in exchange for one consistent deployment/monitoring pattern across the whole server — one docker-compose stack, not containers-plus-bare-host-units.
