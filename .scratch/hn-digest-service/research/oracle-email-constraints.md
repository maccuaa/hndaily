# Research: Oracle Cloud outbound email constraints & delivery mechanism options

Ticket: [04-oracle-email-constraints](../issues/04-oracle-email-constraints.md)

## Recommendation (top-line)

For a **single-recipient, 1-email/day personal digest**, use **SMTP with an app password on an existing Gmail or Fastmail account**. It requires no new DNS records, no new domain, no new third-party account, and no IAM ceremony — just enabling 2-Step Verification and generating a 16-character app password (5 minutes total). It also sends from infrastructure with already-mature IP/domain reputation, which matters more for bulk senders than for you, but costs nothing extra either way.

If you'd rather send from your own domain (e.g., `digest@yourdomain.com`) with minimal ceremony, **Resend's free tier** (3,000 emails/mo, both SMTP and REST API) is the next-best option — one domain verification (2-3 DNS records) and an API key, no IAM group/policy/approved-sender dance.

**OCI Email Delivery is a legitimate free option since you already have the OCI account**, but per the findings below it objectively requires the most setup steps of anything compared here (IAM group+user+policy, email-domain creation, SPF, DKIM, "approved sender" registration, then SMTP-credential generation — 6+ discrete steps), and I could not fully resolve one important ambiguity (exact post-trial free-tier volume/cost — see §2.4). It's a reasonable choice only if you specifically want to avoid any third-party dependency and already own a domain to verify.

Critically: **the port-25 question (§1) turns out to be close to moot for your use case.** Every viable path here — OCI Email Delivery, AWS SES, Resend, Postmark, and Gmail/Fastmail relay — is reached over port **465 or 587** (authenticated mail-submission ports), never port 25. Port 25 blocking only matters if you try to run your own MTA that does direct-to-MX delivery. So even though I could not pin down OCI's exact policy, it shouldn't change your decision.

## 1. Does OCI block outbound port 25 by default?

**Short answer: I could not find a primary-source Oracle statement confirming or denying this**, despite an extensive search of Oracle's official documentation. This is worth being explicit about, since it's exactly the kind of easy-to-get-wrong assumption.

### What I verified for the other three clouds (for comparison)

- **AWS** explicitly blocks it: *"By default, AWS blocks outbound traffic on port 25 for all EC2 instances and Lambda functions on elastic network interfaces. This block prevents spam and applies to AWS accounts that aren't on an allowlist."* Removing it requires submitting a request form to AWS (up to 48 hours to process, per-region). Source: [repost.aws/knowledge-center/ec2-port-25-throttle](https://repost.aws/knowledge-center/ec2-port-25-throttle) (official AWS knowledge base, referencing `docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-resource-limits.html#port-25-throttle`).
- **GCP** explicitly blocks it for external destinations: *"Due to the risk of abuse, connections to destination TCP Port 25 are blocked when the destination is external to your VPC network... However, some projects do not have this restriction."* No general self-service unblock process is documented; Google's own guidance is to use port 587/465 or a third-party relay instead. Source: [cloud.google.com/compute/docs/tutorials/sending-mail](https://cloud.google.com/compute/docs/tutorials/sending-mail).
- **Azure** blocks it by default for **all subscription types except Enterprise Agreement/MCA-E**: *"The Azure platform blocks outbound SMTP connections on TCP port 25 for deployed VMs. This block is to ensure better security for Microsoft partners and customers, protect Microsoft's Azure platform, and conform to industry standards."* Dev/Test EA subscriptions can self-service-unblock via a diagnostic tool in the Azure Portal; all other subscription types (including free tier / pay-as-you-go) **cannot** get it unblocked at all and must use an authenticated SMTP relay on port 587 instead. Source: [learn.microsoft.com/.../troubleshoot-outbound-smtp-connectivity](https://learn.microsoft.com/en-us/troubleshoot/azure/virtual-network/troubleshoot-outbound-smtp-connectivity).

### What I found (and didn't find) for OCI

I searched, page-by-page, Oracle's entire public Email Delivery documentation set (Overview, Getting Started, SMTP connection config, HTTPS/API submission, SMTP credentials, approved senders, SPF, DKIM, troubleshooting), their general Networking docs (Security Lists, Network Security Groups, NAT Gateway, Internet Gateway), the Always-Free-resources doc, the general "Getting Started FAQ," and the default service-limits page. **None of them mention port 25 at all** — not to say it's blocked, and not to say it isn't. This is itself notable: it's exactly the kind of thing Oracle's own "Overview of Email Delivery" page would naturally cite as a reason to use the managed service (as GCP and Azure's docs do), and it doesn't.

What I *can* confirm, as circumstantial (not conclusive) evidence:
- OCI's Security Lists / Network Security Groups are entirely user-configurable virtual firewalls with no documented port-25-specific carve-out anywhere in the Networking docs — unlike AWS/Azure/GCP, where the port-25 restriction is described as a *platform-level* block that exists independently of (and cannot be overridden by) your own security-group/firewall configuration. Sources: [docs.oracle.com/.../securitylists.htm](https://docs.oracle.com/en-us/iaas/Content/Network/Concepts/securitylists.htm), [.../securityrules.htm](https://docs.oracle.com/en-us/iaas/Content/Network/Concepts/securityrules.htm), [.../NATgateway.htm](https://docs.oracle.com/en-us/iaas/Content/Network/Tasks/NATgateway.htm).
- Oracle's own SMTP integration examples for Email Delivery (Postfix, Python) present port 465 as the recommended port but explicitly show 25 and 587 as alternative *inbound* ports to *their* relay working too (comments in the official Python sample: *"if using port 25 or 587, comment out the line above [SMTP_SSL] and uncomment... starttls()"*) — source: [docs.oracle.com/.../python.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Reference/python.htm). Note this describes ports Oracle's *own* mail-submission servers accept, which is a different question from whether your instance can reach arbitrary third-party mail servers on port 25 outbound — it doesn't resolve the general question.
- It's widely reported in the self-hosting/homelab community that OCI does **not** block outbound port 25 the way AWS/GCP/Azure do (this is frequently cited as a reason people run their own mail servers on OCI's free-tier instances) — but I want to flag clearly that **this is community reporting, not something I could verify against an Oracle primary source**, and I'm not presenting it as confirmed fact.

**Honest conclusion:** I cannot responsibly confirm OCI's port-25 policy either way from primary sources. If you need a definitive answer, the two options I'd suggest are (a) empirically test it from your instance once it's up (e.g., `nc -zv -w5 <some-external-mx-host> 25`), or (b) check the Console's **Governance & Administration → Limits, Quotas and Usage** page. As noted above, though, this **doesn't affect the recommendation** — none of the paths in this report need outbound port 25.

## 2. OCI's "Email Delivery" service — setup, verification, limits, cost

**Current name/URL:** "Email Delivery" (part of OCI, under Developer Services → Application Integration in the console). Marketing page: [oracle.com/application-development/email-delivery/](https://www.oracle.com/application-development/email-delivery/) ("Email Delivery, built on Oracle Dyn's proven technology..."). Technical docs root: [docs.oracle.com/en-us/iaas/Content/Email/Concepts/overview.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Concepts/overview.htm). It's confirmed as one of the "Always Free" services in Oracle's Free Tier FAQ: [oracle.com/cloud/free/faq/](https://www.oracle.com/cloud/free/faq/) (listed alongside Compute, Object Storage, etc.).

### 2.1 Domain ownership verification

You create an **Email Domain** (Console: Developer Services → Application Integration → Email Delivery → Email Domains → Create Email Domain). Requirements, per [docs.oracle.com/.../gettingstarted_topic-create-email-domain.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Reference/gettingstarted_topic-create-email-domain.htm):
- Must be a domain **you own/control in DNS** — "measures used to establish verification and authentication require a DNS record update."
- Cannot be a public mailbox domain (gmail.com, hotmail.com, yahoo.com) or `oracle.com`.
- There's no separate "click this verification link" step distinct from DNS — ownership is effectively proven by making SPF/DKIM DNS records live. Notably: *"If DKIM isn't active, you can't create the approved sender"* for a whole-domain sender — DKIM activation is a hard gate. Source: same page, "Create a Custom Return Path" section.
- Additional forbidden sending domains are listed in [docs.oracle.com/.../managingapprovedsenders.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Tasks/managingapprovedsenders.htm): `@oracle.com`, `@*.oraclevcn.com` (private-only, not publicly resolvable), and public mailbox providers generally (their DMARC policies won't delegate to third-party senders); `@oraclecloud.com` is called out as "problematic."

### 2.2 Required DNS records

- **SPF** (TXT record on your domain), value differs by sending region — e.g., for the **Americas** region: `v=spf1 include:rp.oracleemaildelivery.com ~all`. Other regions (Asia/Pacific, etc.) have their own values shown in the Console. Oracle's docs state SPF is *"required for subdomains of `oraclegovcloud.com` and recommended in other cases"* — so not hard-mandatory for ordinary commercial-realm senders, but required for any **sending-limit increase** (see below), and de facto required for good deliverability. Source: [docs.oracle.com/.../configurespf.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Tasks/configurespf.htm).
- **DKIM** (CNAME record), generated via Console → Email Domains → [domain] → DKIM → Add DKIM, with a selector you choose. The exact DNS location is `<selector>._domainkey.<email-domain>` (or a zone-relative form depending on your DNS provider's UI). Source: [docs.oracle.com/.../configure-dkim-using-the-console.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Tasks/configure-dkim-using-the-console.htm) and [.../troubleshooting.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Concepts/troubleshooting.htm) (which spells out the CNAME-path gotchas).
- **DMARC** is *not* something OCI configures or hosts for you — it's only mentioned in passing (e.g., "DMARC From alignment rules" as a reason not to use mismatched From addresses, in [managingapprovedsenders.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Tasks/managingapprovedsenders.htm)). There is no dedicated "Configure DMARC" task page in the Email Delivery docs (unlike SPF and DKIM, which each have one) — you'd add your own `_dmarc.<domain>` TXT record independently, same as with any provider.

### 2.3 Approval / allowlisting process

There is a resource called an **"Approved Sender"** that must exist for every "From:" address you send as, or *"mail is rejected."* Creating one (Console → Email Delivery → Approved Senders → Create Approved Sender) is **self-service** — I found no evidence of a manual Oracle staff review gate for registering a sender, unlike some competitors. It is region-specific (an approved sender created in one region can't send via another) and should not be created in the root compartment. Source: [docs.oracle.com/.../gettingstarted_topic-Create_an_approved_sender.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Reference/gettingstarted_topic-Create_an_approved_sender.htm).

The closest thing to a manual approval process is for **sending-limit increases** beyond the default: you must open a support Service Request and answer questions about your sending practices (CAN-SPAM/CASL compliance, how recipients opted in, expected volume, etc.), and SPF+DKIM must already be configured. This is irrelevant at 1 email/day. Source: [docs.oracle.com/.../overview.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Concepts/overview.htm) ("Email Delivery Service Capabilities and Limits" section). Separately, **dedicated IP addresses** (which you don't need) go through a deliverability-team review and are explicitly discouraged for low/sporadic volume — same source, "Dedicated IP Addresses" section.

### 2.4 Free-tier limits and cost beyond free tier

Per the same overview page, Oracle documents two tiers:
- **Free trial accounts**: 200 emails/day (an "email" = one TO/CC/BCC recipient, or a 2 MB chunk of message data), 2,000 approved senders, **max 2 SMTP credentials per user**, 10 emails/minute rate limit, 2 MB max message size.
- **"Enterprise" (paid) accounts**: 50,000 emails/day, 10,000 approved senders, 18,000 emails/minute.

**Gap I could not close:** Oracle's docs split limits into "Trial" vs. "Enterprise" but don't clearly state what an **"Always Free"-tier account** (i.e., you've added a payment method and left Trial, but are only consuming Always-Free resources) gets for Email Delivery specifically — whether it keeps the 200/day trial allowance indefinitely, jumps to metered/paid billing from email #1, or something else. I also could not extract Email Delivery's per-unit overage price: Oracle's [public price list page](https://www.oracle.com/cloud/price-list/) renders all numeric prices via client-side JavaScript that isn't present in the static HTML, and I couldn't locate a static "Email Delivery" pricing page or PDF that lists a fixed per-1,000-emails rate. **Practically, this gap shouldn't matter for you**: at 1 email/day (~30/month) you are so far under the 200/day trial ceiling — and any plausible per-email metered rate at that volume would be fractions of a cent per month — that the ambiguity has no real cost impact. If you want a firm number before committing, use the Console's interactive "Cost Estimator" (linked from the price list page) or open a pre-sales question, since I can't responsibly state a figure I couldn't verify.

## 3. How you'd actually send: SMTP relay, REST API, or both

**Both are supported**, confirmed directly from Oracle's docs and SDK source:

### SMTP relay
- You generate **SMTP credentials** (a username/password pair *distinct from* your normal OCI Console login) via Console → Profile/User Settings → SMTP Credentials → Generate Credentials. The password is shown **exactly once** — copy it immediately. Free tier caps this at 2 credential-sets per user. Source: [docs.oracle.com/.../gettingstarted_topic-create-smtp-credentials.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Reference/gettingstarted_topic-create-smtp-credentials.htm).
- Auth mechanism is standard **SMTP AUTH PLAIN** (RFC 4616), over mandatory TLS. Source: [docs.oracle.com/.../overview.htm#SMTP_Authentication_and_Connection_Endpoints](https://docs.oracle.com/en-us/iaas/Content/Email/Concepts/overview.htm).
- Oracle's recommended port is **465** ("the new default mail submission port," implicit TLS negotiated at connection start rather than STARTTLS) — [docs.oracle.com/.../gettingstarted_topic-Configure_the_SMTP_connection.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Reference/gettingstarted_topic-Configure_the_SMTP_connection.htm). Ports 587 and 25 are also shown as usable in Oracle's own Python example (with STARTTLS) but 465 is what they steer you to.
- **Endpoint hostname**: Oracle's docs are inconsistent about the literal string, and explicitly tell you to read the live value from the Console rather than hardcode it ("For the correct endpoint value, consult the Authentication and Connection Endpoints"). Two different official Oracle pages show two different formats for the *same* region (us-ashburn-1):
  - Postfix guide: `smtp.email.us-ashburn-1.oci.oraclecloud.com:465` — [docs.oracle.com/.../postfix.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Reference/postfix.htm)
  - Python guide: `smtp.us-ashburn-1.oraclecloud.com` (port 465) — [docs.oracle.com/.../python.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Reference/python.htm)
  - **Recommendation: copy the exact value from Console → Developer Services → Email Delivery → Configuration rather than trusting either doc literally.**

### REST API
- Called the **"Email Delivery Submission API"**, reachable over HTTPS, authenticated via any standard OCI SDK mechanism — API key, **instance principal** (meaning your OCI compute instance can authenticate using its own identity, no stored secret needed at all), or resource principal. Source: [docs.oracle.com/.../email-submission-using-https.htm](https://docs.oracle.com/en-us/iaas/Content/Email/Concepts/email-submission-using-https.htm).
- I confirmed the actual data-plane endpoint template directly from Oracle's public Go SDK source: `https://cell0.submit.email.{region}.oci.{secondLevelDomain}` (e.g. `cell0.submit.email.us-ashburn-1.oci.oraclecloud.com`), API version `20220926`, operation `SubmitEmail`. Source: [github.com/oracle/oci-go-sdk .../emaildataplane_emaildp_client.go](https://raw.githubusercontent.com/oracle/oci-go-sdk/master/emaildataplane/emaildataplane_emaildp_client.go) (the separate *control-plane* endpoint, for managing domains/senders, is `https://ctrl.email.{region}.oci.{secondLevelDomain}`, from [.../email/email_client.go](https://raw.githubusercontent.com/oracle/oci-go-sdk/master/email/email_client.go)).
- **Relevant to the Bun/TypeScript stack specifically**: Oracle publishes an official TypeScript/JavaScript SDK, `oracle/oci-typescript-sdk`, which includes an `emaildataplane` module installable as `npm install oci-emaildataplane`. Its own README states it requires *"A key pair used for signing API requests, with the public key uploaded to Oracle"* — i.e., generating an OCI API signing key, uploading the public half in Console, and configuring the SDK with your tenancy/user OCIDs, key fingerprint, and private key file. Source: [github.com/oracle/oci-typescript-sdk .../lib/emaildataplane/README.md](https://raw.githubusercontent.com/oracle/oci-typescript-sdk/master/lib/emaildataplane/README.md).

**Practical takeaway:** SMTP is meaningfully *less* setup work than the REST API path here, because the REST/SDK route requires generating and managing an OCI API signing key pair (private key file + fingerprint + 3 OCIDs), whereas SMTP just needs a username/password you paste into an env var and hand to any SMTP library (e.g., `nodemailer`, which works fine under Bun). For a daily cron job, default to SMTP unless you specifically want to avoid storing long-lived SMTP credentials and are comfortable with API-key/instance-principal setup instead.

## 4. Alternatives — setup-complexity comparison

| | Setup steps | Free tier | Notes |
|---|---|---|---|
| **AWS SES** | New AWS account → verify domain (DNS TXT) → DKIM (CNAME) → **request "production access"** to exit sandbox mode (manual review, typically ~24h) → SMTP creds or API/SDK | 3,000 msgs/month **free only for the first 12 months** of the AWS account, then billed | Source: [aws.amazon.com/ses/faqs/](https://aws.amazon.com/ses/faqs/) ("Receive up to 3,000 message charges for free each month for the first 12 months"). Also requires standing up an entirely separate cloud account/billing relationship. Sandbox-mode requirement is the main extra friction vs. others here. |
| **Resend** | New account → verify 1 domain (SPF TXT + DKIM CNAME) → API key | **3,000 emails/month, perpetual** (not time-limited), capped at 100/day on free tier | Source: [resend.com/pricing](https://resend.com/pricing). Includes both REST API and SMTP relay, DKIM/SPF/DMARC support built in. Fewest steps of the "real" transactional-email providers — no IAM/group/policy ceremony like OCI. |
| **Postmark** | New account → verify domain (SPF/DKIM) | **100 emails/month, perpetual, $0, no overages allowed** | Source: [postmarkapp.com/pricing.txt](https://postmarkapp.com/pricing.txt). 100/month comfortably covers 1/day (~30/month). |
| **Gmail (app password)** | Enable 2-Step Verification → generate app password → point any SMTP client at `smtp.gmail.com:587` (STARTTLS) or `:465` (implicit TLS) with your Gmail address as username | Free, uses your existing account | Sources: [support.google.com/accounts/answer/185833](https://support.google.com/accounts/answer/185833) (app-password mechanics — note Google's own framing: *"App passwords aren't recommended and are unnecessary in most cases"*, though that guidance targets desktop mail clients with a "Sign in with Google" alternative, not SMTP relay/automation, where app passwords remain the standard mechanism); sending limits are in the hundreds-to-low-thousands/day depending on account type per [Google's Workspace sending-limits page](https://knowledge.workspace.google.com/admin/gmail/gmail-sending-limits-in-google-workspace) — irrelevant at 1/day. **Zero DNS, zero new domain, zero new account.** |
| **Fastmail (app password)** | Settings → Privacy & Security → Connected apps & API tokens → New app password (scope: "Mail, Contacts & Calendars") → use with `smtp.fastmail.com` | Requires a **paid** Fastmail plan above "Basic" — Fastmail's own docs state *"Users on a Basic plan will not be able to use Fastmail on third-party mail clients or create app passwords... Basic plans do not include access to IMAP, SMTP..."* | Source: [fastmail.help/.../App-passwords](https://www.fastmail.help/hc/en-us/articles/360058752854-App-passwords). Otherwise same simplicity as Gmail. |

## Gaps and things I couldn't verify

1. **OCI's default outbound-port-25 policy** — not stated (positively or negatively) anywhere I could find in Oracle's official docs, despite checking the Email Delivery docs, Networking/Security List/NSG/NAT-Gateway/Internet-Gateway docs, Free Tier docs, and general FAQ. I was also unable to use general web search engines for this investigation — DuckDuckGo, Bing, Yahoo, Yandex, Startpage, Qwant, Mojeek, SearXNG, and Marginalia all either bot-walled the request or returned non-organic filler content, so I relied entirely on direct fetches of docs.oracle.com, oracle.com, and GitHub-hosted SDK source. If a firm answer matters, empirically testing from a running instance, or checking Console → Limits/Quotas/Usage, would be the next step (this can fold into ticket 07's server-facts checklist).
2. **Exact OCI Email Delivery overage pricing** and the precise Always-Free (vs. Trial vs. Enterprise) volume threshold — the public price list page's values are JS-rendered and not present in static HTML; I could not find a static/PDF rate card either. Immaterial at this volume, as noted in §2.4.
3. The **SMTP endpoint hostname format** is inconsistently documented by Oracle itself across two of their own pages (§3) — flagging rather than picking one as authoritative; use the Console's live value.
4. Mailgun was not deep-dived (its pricing page is JS-rendered and didn't yield static content), since Resend and Postmark already satisfy the "simplest free tier" comparison point.
